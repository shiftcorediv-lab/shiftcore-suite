# Another Portal Blue/Green 公開設計

## 文書の状態

- 状態: ローカル実装・検証完了、外部設定未実施
- 正式な利用者向けURL: `https://portal.another-inc.jp/`
- 対象: Another Portal の静的フロント公開
- 対象外: 本番データ移行、GAS/API の二重化
- 実装: 完了（Cloudflare Workers Static Assets、Service Bindingルーター、公開物生成、検証）
- 外部設定・公開: Cloudflare管理者OAuth認証は完了。Worker公開、DNS・Firebase・本番入口は未変更

## 目的

利用者の入口を一つに固定したまま、実運用中の画面とは別の公開枠で次版を確認し、安全に入れ替えられるようにする。

この仕組みは、別々のコードベースを二つ保守するものではない。同じリポジトリの承認済みコミットから作った公開物を、Blue と Green の二つの枠へ交互に配置する。

## 現状確認

2026-09-02 時点のリポジトリから、次を確認した。

- 静的フロントは GitHub Pages の `shiftcore-suite` 配下で公開されている。
- `main` が現在の公開元であり、リポジトリ内に独自の GitHub Actions 公開ワークフローはない。
- TEST／本番のAPI切替は `common/environment.js` に集約され、`shiftcore_env=staging` と同一タブのセッション情報で判定している。
- 本番APIは Cloudflare Workers と Google Apps Script の既存URLを利用している。
- `shared/js/shiftcore-urls.js` などに GitHub Pages の絶対URLが残っている。
- `apps/another-portal` は、現在の業務ポータルとは別の凍結中の仮想オフィス試作である。製品名とディレクトリ名が衝突しているため、この公開切替作業では変更しない。

## 採用する構成

```text
利用者
  |
  v
portal.another-inc.jp  （唯一の利用者向けURL）
  |
  v
公開先ルーター        （ACTIVE_SLOT を参照）
  |-------------------------------|
  v                               v
Blue 公開枠                      Green 公開枠
実運用または待機                 待機または実運用
  |                               |
  |-------------------------------|
                  |
                  v
       既存の本番API／本番データ

preview.portal.another-inc.jp
  |
  v
現在の待機枠（管理者確認専用）
```

### 構成要素

| 要素 | 役割 |
|---|---|
| 共通入口 | 利用者が保存・共有する唯一のURL。接続先を変えてもURLを変えない |
| 公開先ルーター | Blue／Greenのどちらへ接続するか決め、パスとクエリを維持して転送する |
| Blue／Green公開枠 | 同じソースから作った静的ファイルを交互に配置する |
| 管理者用プレビュー入口 | 待機枠を公開前に確認する。一般利用者には案内しない |
| TEST環境 | 本番データと分離した書き込み確認用として現在の仕組みを残す |

初期構成では Cloudflare Workers Static Assets に Blue／Greenの二つの静的公開枠を置き、Cloudflare Worker を共通入口のルーターにする。ルーターから各公開枠へは、公開URLではなくService Bindingで接続する。GitHub Pages は移行完了まで既存公開先として残し、安定確認後に扱いを決める。

## 公開先の管理方法

初期版では、画面上の切替管理機能を作らない。

- ルーターの `ACTIVE_SLOT` は `blue` または `green` のみを受け付ける。
- 切替は権限を持つ管理者が、管理された公開手順から実施する。
- 切替操作には、対象スロット、Gitコミット、実行者、時刻、確認結果を残す。
- 利用者ごとの振り分けや段階公開は、初期版の対象外とする。
- 切替管理画面は、認証、権限、操作確認、監査ログを設計してから将来追加する。

## URLと認証の原則

1. 利用者を Blue／Green の別ドメインへリダイレクトしない。
2. ブラウザ上のオリジンは共通入口のまま維持する。
3. Firebase Authentication の許可ドメインへ共通入口を追加する。
4. 管理者プレビューでログインする場合のみ、プレビュー入口も許可対象として検討する。
5. GitHub Pages の絶対URLは、共通入口または同一オリジンの相対URLへ段階的に置き換える。
6. TEST環境のリンクでは `shiftcore_env=staging` を失わない。

この方式により、公開切替による再ログインと `auth/unauthorized-domain` の発生を避けやすくする。

## Blue／Greenで保証する範囲

初期版で瞬時に戻せるのは静的フロントだけである。

| 変更内容 | Blue／Green切替で復旧可能か | 条件 |
|---|---|---|
| HTML／CSS／JavaScriptの表示不具合 | 原則可能 | API契約が旧版と互換であること |
| フロントのリンク・導線不具合 | 原則可能 | バックエンド変更を伴わないこと |
| GAS／Worker APIの不具合 | 不十分 | APIを別途戻す必要がある |
| データ形式の破壊的変更 | 不可 | 事前の互換設計またはデータ復旧が必要 |
| 誤更新・データ欠損 | 不可 | 書き込み停止、調査、データ復旧が必要 |

バックエンドを変更する場合は、少なくとも一つ前のフロントが動くAPI契約を維持する。削除や必須項目変更は、追加、移行、利用開始、旧仕様削除の順に分ける。

## 公開物の識別

各公開枠には、次を確認できるリリース情報を含める。

- 製品バージョン
- GitコミットSHA
- 公開スロット
- ビルド日時
- 環境名

利用者画面には製品バージョンのみを小さく表示し、詳細は管理者が確認できる `release.json` または診断画面へ分離する。秘密情報や内部API設定は含めない。

## 通常の公開手順

例として、Blueが実運用中の場合を示す。

1. `main` から公開候補コミットを確定する。
2. 自動テスト、構文検査、主要画面の静的確認を通す。
3. TEST環境で、ログイン、ダッシュボード、Order、Shift、勤怠、実績報告の主要導線を確認する。
4. 同じコミットから作った公開物を、待機中のGreenへ配置する。
5. 管理者用プレビュー入口で、アセット欠落、画面遷移、Firebaseログイン、API接続を確認する。
6. 本番APIに対する確認は、最初に読み取り操作だけで行う。本番書き込み確認が必要な場合は、対象と後始末を決めて別途承認を取る。
7. 公開候補コミット、確認結果、復帰先がBlueであることを記録する。
8. `ACTIVE_SLOT` をGreenへ切り替える。
9. 共通入口から主要画面を確認し、新規エラーと操作時間を監視する。
10. 問題がなければGreenを実運用、Blueを待機枠として記録する。

## 巻き戻し手順

### フロントだけの問題

1. 新規書き込み操作の案内を止める。
2. `ACTIVE_SLOT` を直前の実運用枠へ戻す。
3. 共通入口からログインと主要画面を確認する。
4. 発生時刻、症状、対象コミット、巻き戻し時刻を記録する。
5. 問題の公開物は上書きせず、調査できる状態で保持する。

### APIまたはデータに影響する問題

1. 必要に応じて書き込みを停止し、読み取り専用またはメンテナンス表示へ切り替える。
2. フロントだけでなく、対象APIとデータへの影響を確認する。
3. APIの安全な版へ戻すか、互換修正を公開する。
4. データ復旧が必要な場合は、対象範囲と復旧方法を確認してから実施する。
5. Blue／Greenの切替だけで復旧したとは判断しない。

## メンテナンス表示

全面停止ではなく、可能な限り次の二段階を用意する。

- 読み取り専用: 閲覧は可能だが、保存・勤怠・報告操作を止める。
- 全面メンテナンス: ログイン前後で同じ案内を表示し、復旧見込みと連絡先を示す。

勤怠や実績報告は締刻に影響するため、停止中の代替報告方法と、復旧後の代理登録手順を運用ルールとして別途決める。

## キャッシュ対策

- HTMLは短時間で更新確認できる方針にする。
- JavaScriptとCSSは内容に応じた版番号またはファイル名を付け、旧版混在を防ぐ。
- ルーターはBlue／Greenのレスポンスを不用意に同じキャッシュキーで共有しない。
- 切替後の確認では、通常読込とキャッシュを無効化した読込の両方を行う。
- Service Workerを導入する場合は、旧版を保持する期間と更新失敗時の挙動を別途設計する。

## 監視項目

最低限、次を切替前後で確認する。

- 共通入口と主要HTMLのHTTP状態
- JavaScript／CSS／画像の404
- Firebaseログイン失敗
- APIエラー率とタイムアウト
- ダッシュボード初期表示時間
- Order保存、Shift反映、勤怠、実績報告の失敗
- 表示中の製品バージョンと実運用スロットの一致

速度改善そのものはv2候補とする。ただし、タイムアウト、二重送信、保存結果不明を起こす遅さはv1の運用不具合として扱う。
