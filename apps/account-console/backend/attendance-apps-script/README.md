# ShiftCore 勤怠API

`Code.gs` は、ShiftCore勤怠ダッシュボード用のGoogle Apps Script Web APIです。

## 本番リソース

- 勤怠管理スプレッドシート: 「ShiftCore 勤怠管理」
- 位置情報スプレッドシート: 「ShiftCore 位置情報（限定閲覧）」
- WebアプリURL: `https://script.google.com/macros/s/AKfycbzYSk46G7ZZx55vQIOC5pRqyA15rn15ORbTe_f72PVxmj5v0EISBbL4tpGA_ehOtnBnAQ/exec`

## 運用上の注意

- 正式な打刻時刻はApps Script側の日本時間で記録します。
- 出発・入店・予定外稼働の位置情報は別ファイルへ保存し、原則7日で削除します。出発位置は出発報告ID、入店・予定外稼働位置は勤怠記録IDで関連付けます。`setupAttendanceTriggers` を一度実行して、通知と自動削除のトリガーを登録してください。
- 管理者通知先は勤怠管理ブックの `管理者` シートを優先します。未作成または空の場合は、Apps Scriptの実行所有者へ通知します。
- `Code.gs` を変更した場合はApps Script側へ反映し、既存Webアプリの新バージョンを作成してください。デプロイIDは変更しません。
- 公開範囲は「全員」ですが、各API操作はFirebase IDトークンを既存ログイン基盤で検証します。
- 本番から分離した通し確認は、[`STAGING_ENVIRONMENT.md`](../../../STAGING_ENVIRONMENT.md) の専用入口・専用GAS・専用スプレッドシートを使用します。

## 直属承認接続

- Account Console側と勤怠API側のScript Propertiesへ、同一の十分に長いランダム値を `ATTENDANCE_APPROVAL_SERVICE_SECRET` として設定します。値をソース、シート、ログへ保存しないでください。
- Account側は、この秘密を保持する勤怠GASを終端監査ログの信頼主体として扱います。秘密を取得した主体は任意の終端結果を送信できるため、閲覧者を限定し、漏えい時は両側を同時にローテーションしてください。
- 勤怠GASからAccount GASへは既存Account Webアプリの `/exec` URLを直接呼び出します。ログイン用Cloudflare Workerは許可アクションが限定されているため、直属承認契約の中継には使用しません。
- 新規申請では `applicant_internal_user_id`、`request_version`、`approval_reviewer_internal_user_id`、`applicant_organization_version` 列を自動追加して保存します。既存の承認待ち行は自動変換せず、本人確認後の再申請が必要です。
- Account Consoleと勤怠APIの両方を反映するまで、実効承認へ切り替えないでください。片側だけの反映では新規申請または承認をfail-closedで拒否します。

## 実績報告データ契約

実績報告は、固定的なフォーム項目を `実績報告` シートの列として増やしません。現在の入力対象は、管理画面で明示的にドコモ用テンプレートへ対応付けた案件だけです。案件名に「ドコモ」が含まれるかどうかでは判定しません。

- `実績テンプレート`: キャリア・案件群ごとの入力様式を管理します。初期値は `docomo` です。
- `実績対象案件`: 安定した開発予定IDとテンプレートを有効期間付きで対応付けます。停止前に終了した未提出勤怠は残し、停止中の勤怠は対象外にし、再開後の勤怠だけを再び対象にします。
- `実績報告`: 1勤怠記録につき1件の報告ヘッダー。最新版の改訂IDと番号を指します。既存の文章列は旧データとの互換表示に残し、新形式の提出で上書きしません。
- `実績報告改訂`: 初回提出、本人修正、差戻し後再提出を版ごとに保持します。差戻し理由・日時・差戻し者も対象版へ保存します。同じ送信トークンの再送は同じ版へ復帰します。
- `実績項目`: テンプレート、現在の項目名、数値／文章、カテゴリ、表示順、必須、有効、定義版、本人ダッシュボード表示を管理します。
- `実績回答`: 1改訂・1項目につき1行。回答時点の項目名、型、カテゴリ、表示順、定義版をスナップショット保存します。

項目を追加、改名、並べ替え、停止しても、過去回答は `実績回答` のスナップショットから表示・集計します。修正画面では直前の回答を初期表示し、保存すると新しい版を作成します。本人は自分の報告だけについて、過去の版と各版への差戻し理由を読み取り専用で確認できます。通常集計と本人ダッシュボードは最新版の提出済み回答だけを使い、管理画面と履歴CSVでは旧版も確認できます。差戻し中は承認待ちではなく「要修正」として未完了数へ含めます。

案件の対象設定を停止しても、すでに存在する報告と停止前に終了した未提出勤怠は一覧・集計・CSVに残ります。停止後の終了済み勤怠を新しい未提出として数えません。停止後に再開した場合は新しい有効期間を追加し、停止中の勤怠を後から未提出へ変えません。

旧形式の文章保存済みデータは推測変換・削除せず、そのまま保持します。旧行を新形式で再提出しても、既存の `実績内容` と `課題・申し送り` は上書きしません。

数値は0以上の整数です。任意数値の空欄は0として保存しますが、`入力状態=defaulted` を記録して、利用者が0を入力した場合と区別します。

本人ダッシュボードの成績APIは、ログイン本人の対象勤怠だけをサーバー側で抽出します。全員分をブラウザへ返して画面側で絞り込む方式にはしません。直属管理者向けの配下一覧は将来拡張とし、05初回には含めません。

### 初回運用設定

1. 管理者が `setupWorkReportData` を一度実行し、必要なシートと列を明示的に初期設定します。通常利用者のフォーム表示や送信では、シート作成・列追加を行いません。
2. 実績報告管理画面の「実績報告の対象案件」で、稼働日・人員名・案件名を確認し、ドコモ案件だけを対象へ設定します。案件IDの手入力は不要で、一度の設定が同じ案件の全日程・全担当者へ適用されます。
3. 「実績項目管理」で、本人ダッシュボードに表示する数値項目、表示名、表示順を確認します。
4. 対象外案件の終了報告後に実績報告へ遷移しないこと、対象案件だけが未提出集計へ入ることを確認します。

本番シート作成・案件対応の設定は本番データ変更です。コード反映とは分け、明示承認後に実施してください。
