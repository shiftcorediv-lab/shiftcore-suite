# 03 権限設計 正式案

- 更新日: 2026-08-10
- 対象: ShiftCore Suite 全体
- 状態: 基本方針と4段階の組織階層、全社閲覧、直属承認をえいち承認済み。移行・API詳細設計中
- 実装状態: 03本体の権限変更は未実施

## 1. 結論とおすすめ案

`role` は「管理者かどうか」ではなく、利用者の所属・契約上の区分として扱う。操作権限は `role` から分離する。

おすすめする正本は次の二層構造である。

1. `users_master`
   - 本人情報、アカウント状態、所属、利用可能アプリを管理する。
   - 既存の `allowed_modules`、`ordercase_permission`、`shiftbuilder_permission` は移行期間中の後方互換として維持する。
2. `permission_assignments`（新設候補。名称は承認後に確定）
   - 「どの利用者が、どのアプリで、何を、どの範囲までできるか」を操作単位で管理する。
   - 04以降の報告、労務、位置情報、月間集計も同じ仕組みへ追加する。

参照経路は次へ統一する。

```text
Firebase Authentication
  → Account APIでIDトークンと有効ユーザーを確認
  → users_masterでアプリ利用可否を確認
  → permission_assignmentsで操作とデータ範囲を確認
  → 各アプリAPI／GASが最終判定
  → 許可されたデータだけを返す／変更する
```

フロント画面は利用者への案内を担当する。権限の最終防御は必ずAPI／GAS側で行う。

### 組織階層と操作権限は別に保存する

組織階層は次の4段階とする。

```text
役員 > マネージャー > リーダー > メンバー
```

- `role` は既存のシステム上の利用者区分として残し、組織階層の判定に流用しない。
- 既存の自由入力 `position` は表示用とし、権限判定の正本にはしない。
- 組織階層、直属管理者、有効期間を、表記揺れのない正式な組織情報として管理する。
- `shiftbuilder_permission=manager` はShift専用の旧権限値であり、組織上のマネージャーとは別物。
- Shiftの配置・入替・解除は組織階層ではなく、明示的なShift編集権限で判定する。
- リーダー以上は全社閲覧、リーダー未満は本人の公開済み予定だけとする。
- 全社閲覧と申請承認を分離し、申請承認は申請者の直属管理者本人だけに許可する。

## 2. 確認済み事実

### ログインとセッション

- 共通ログインはFirebase AuthenticationのGoogleログインを使う。
- フロントはFirebase IDトークンを取得し、Account APIまたは各アプリAPIへ渡す。
- Account APIはIDトークンからメールを解決し、`users_master` の有効ユーザーを返す。
- Dashboard、登録申請管理、OrderCase、ShiftBuilder、勤怠APIは認証済みユーザーを再取得する経路を持つ。
- URLクエリのroleや利用者IDは画面遷移用に残るが、登録申請管理の権限判定には使わないよう修正済み。

### Account Consoleの保存情報

`users_master` には少なくとも次が存在する。

- 本人識別: `internal_user_id`、`email`、`auth_uid`
- 状態: `status`、`workStatus`、`engagement_status`
- 所属・区分: `role`、`organization_id`、`base_area`、`affiliation_type`、`contract_type`、`grade_role`
- アプリ入口: `allowed_modules`
- 詳細権限: `ordercase_permission`、`shiftbuilder_permission`

コード上の正式なrole値は次の6種類である。

- `developer`
- `admin`
- `member`
- `partner_individual`
- `partner_company_admin`
- `agency`

`employee`、`internal`、`dev`、`partner_company` 等は表示上の旧別名や他機能の独自値として残るが、Account Consoleの保存許容値ではない。

`developer` は業務上の組織階層とは別のシステム特権roleとし、有効状態である限り全アプリの閲覧・作成・編集・確定・公開・アーカイブ・権限管理を行える。個別の `allowed_modules`、`ordercase_permission`、`shiftbuilder_permission` が空欄または弱い値でも、developerの実効権限は制限しない。ただし、停止中アカウントの拒否、自己権限変更の禁止、組織グラフ検証、監査ログはdeveloperにも適用する。

一般のAccount Console操作者は、自分または他人を `developer` へ変更できず、既存developerアカウントも変更できない。developerの新設・変更は既存developerだけに許可し、developer本人が自分のroleを変更する操作も拒否する。

developerは運用主体ではないため、ShiftBuilderの配置候補・人員軸・配置済み表示とPMOの月次人員名簿には表示しない。認証主体、操作主体、監査ログ上の実行者としては保持し、ユーザーや配置履歴自体を削除しない。既に作成済みのPMO月次シートは静的な値でroleを保持していないため、自動改変せず、別途読み取り確認後に移行対象を確定する。

### 現在のアプリ別制御

#### Account Console

- Dashboard入口は `admin`／`developer` を要求する。
- Account Console APIは、有効かつ `account_console` を持つ利用者なら一覧取得・更新ができる。
- 登録申請管理は、画面・APIとも `admin`／`developer` または `account_console` のOR条件である。
- APIはIDトークン由来の操作者を変更履歴へ記録する。
- 現在は「閲覧だけ」「利用者編集」「権限編集」を分ける詳細権限がない。

#### OrderCase

既存値は `all`、`edit`、`view`、`view_without_amount`。

- すべてのAPI操作で、有効ユーザー、`ordercase` モジュール、詳細権限を確認する。
- `view_without_amount` はAPIレスポンス段階で金額項目を空にする。
- `all` と `edit` は案件作成・編集が可能。
- `all` だけが案件ランクを変更できる。
- 現在の画面では `all` と `edit` の両方が店舗編集・店舗アーカイブ、案件キャンセル・アーカイブを実行できる。
- 案件キャンセル・アーカイブ時は関連する有効アサインをアーカイブする。

#### ShiftBuilder

本番GASを読み取り監査した。既存値は `all`、`manager`、`edit`、`view`、`self`。

- すべての月次取得・候補者取得・書き込み操作でIDトークンを確認する。
- 有効ユーザー、`shift` モジュール、既知の詳細権限値を要求する。
- `all`、`manager`、`edit` は現在すべて同じ編集権限である。
- 作成、解除、入替、ICSメール送信はGAS側でも編集権限を要求する。
- `view` と `self` は書き込みを拒否される。
- `self` でも現在は全体の月次案件、全アサイン、候補者を取得できる。本人限定になっていない。
- `view` でも候補者情報を含む全体データを取得できる。
- `confirmed`、`published` の状態定数とシートは存在するが、確定・公開を行うAPI actionは存在しない。
- したがって `manager` の表示名「確定・公開管理」は、現在の実装能力とは一致していない。

#### 勤怠・報告

- 本人のDashboard、打刻、修正申請、実績報告はIDトークン由来の本人で処理する。
- 実績報告は本人の勤怠記録IDだけを受け付けるよう本番反映済み。
- 管理画面、申請承認、終了漏れ設定は独自の管理role一覧で守られている。
- 独自一覧にはAccount Consoleの正式roleにない `manager`、`team_leader`、`leader`、`executive`、`labor`、`hr`、`dev` が含まれる。
- 正確な位置情報はさらに狭い独自role一覧で制御される。
- `manager` 等は本番 `users_master` の正式保存roleではないため、想定した管理者へ権限が届かない可能性がある。

## 3. 現在の穴と矛盾

重大度順。

1. `self` が本人限定になっておらず、全体の案件・配置・候補者を取得できる。
2. Account Console APIは `account_console` だけで全ユーザーと全権限を変更できるが、画面入口はrole必須で不一致。
3. ShiftBuilderの `all`、`manager`、`edit` がサーバー上で同じ権限。確定・公開APIも未実装。
4. ShiftBuilder詳細権限が空欄の有効利用者が6人おり、Dashboardには入口が出るがGASは利用を拒否する。
5. OrderCaseの `edit` が通常編集だけでなく、金額、店舗アーカイブ、案件アーカイブまで実行できる。
6. 勤怠管理は正式roleではない独自値へ依存し、Account Consoleとの対応が定義されていない。
7. `allowed_modules` の大文字小文字正規化が画面と一部GASで一致しない。
8. 画面遷移URLにrole等を含む古い方式が残る。最終防御には使っていないが、利用者情報の表示が一時的に古くなる可能性がある。
9. 権限不足エラーのコードと文言がアプリごとに異なる。
10. 所属組織、担当エリア、本人というデータ範囲がAPI契約として定義されていない。

## 4. 利用者に分かる権限表（決裁済み）

組織階層は既存 `role` ではない。Shift編集権限、システム管理、正確な位置情報閲覧は階層と別に付与する。

| 組織階層 | 全社閲覧 | OrderCase | ShiftBuilder | Account Console・承認 |
|---|---|---|---|---|
| 役員 | 可 | マネージャー操作＋案件ランク変更 | 確定・公開。配置はShift編集権限がある場合のみ | マネージャー任命・解除、全社権限方針。直属マネージャーの申請承認 |
| マネージャー | 可 | 案件登録・編集、金額閲覧・編集、指名・NG、アーカイブ | 確定・公開。配置はShift編集権限がある場合のみ | メンバー・リーダーの権限管理。直属リーダーの申請承認 |
| リーダー | 可 | 案件登録、金額閲覧 | 配置はShift編集権限がある場合のみ | 直属メンバーの申請承認 |
| メンバー | 不可 | 原則利用不可 | 本人の公開済み予定。配置はShift編集権限がある場合のみ | 本人の報告・申請 |

リーダー以上は全社の案件・シフト・配置・非推奨理由を閲覧できるが、他系統の申請を承認することはできない。

## 5. 操作別の正式案

### Account Console

| 操作 | おすすめ権限 |
|---|---|
| 利用者一覧を見る | アカウント閲覧 |
| 利用者を登録・基本情報を編集 | アカウント編集 |
| role・モジュール・詳細権限を変更 | 権限管理 |
| 利用者を停止・再開 | アカウント停止管理 |
| 登録申請を承認・却下 | 登録申請管理 |
| 変更履歴を見る | 監査閲覧 |

最低限、基本情報編集と権限変更は分離する。自分自身の権限昇格、最後の権限管理者の停止、全管理者喪失を拒否する。

### OrderCase

| 操作 | おすすめ権限 |
|---|---|
| 案件・店舗を見る | 案件閲覧 |
| 金額を見る | 金額閲覧 |
| 案件を登録 | 案件登録 |
| 案件条件を編集 | 案件編集 |
| 金額を編集 | 金額編集 |
| 案件ランクを変更 | 案件管理 |
| 店舗を作成・編集 | 店舗編集 |
| 案件をキャンセル・アーカイブ | 案件アーカイブ |
| 店舗をアーカイブ・復元 | 店舗アーカイブ |

`edit` へすべてを含め続けず、金額とアーカイブを分離するのが安全。ただし既存 `edit` 利用者2人の業務確認後に移行する。

### ShiftBuilder

既存ラベルと業務上の意味を合わせる案。

| 既存値 | 正式な意味のおすすめ |
|---|---|
| `all` | 全操作、例外解除、設定・監査を含む |
| `manager` | 全体閲覧、配置、解除、入替、確定、公開、配布 |
| `edit` | 下書きの配置、解除、入替。確定・公開不可 |
| `view` | 全体閲覧のみ。候補者の連絡先等は返さない |
| `self` | 本人の公開済み予定だけ。候補者一覧や他人の配置は返さない |

確定と公開は別操作にする。

- 確定: 管理者が内容を固定し、通常編集者による変更を止める。
- 公開: 確定済みシフトを本人画面、勤怠予定、配布対象へ反映する。
- 確定取消・公開取消: 原則 `all` のみ。理由と監査ログを必須にする。

### 勤怠・実績・労務

- 本人操作と管理操作を分離する。
- リーダー以上の稼働状況閲覧は全社範囲とする。
- 申請承認は申請者の直属管理者本人に限定し、対象者との直属関係をAPI側で検証する。
- 役員本人の申請は自己承認を禁止し、指定された別の役員だけが承認する。
- 役員の申請・承認は、申請者、承認者、対象、変更前後、理由、日時、結果を監査ログへ残し、他のactiveな役員と独立した監査担当へ通知する。ログだけで談合を完全には防げないため、申請者と承認者の分離、定期レビュー、ログ改ざん検知を併用する。
- activeな役員が1人だけなら役員本人の申請を承認経路なしとして拒否する。役員が2人だけなら、相互承認に加えて独立した監査担当への通知を必須とする。
- 勤怠申請承認と正確な位置情報閲覧を分離する。
- 位置情報は全体管理者でも自動許可せず、明示権限にする。
- 実績報告の修正、差戻し、確定は04の業務仕様確定後に追加する。

## 6. データ範囲

操作権限とは別に、次の範囲を持たせる。

| 範囲 | 意味 |
|---|---|
| `all` | 全社・全組織・全エリア |
| `organization` | `organization_id` が一致する利用者・案件 |
| `area` | 担当 `base_area` または案件エリアが一致 |
| `self` | ログイン本人だけ |

同じ利用者へ複数範囲が必要な場合を考慮し、権限割当表では `scope_type` と `scope_value` を分ける。

## 8. 移行と後方互換

1. 既存 `users_master` は変更せず、値別件数と利用者別移行表を作る。
2. 新権限表を追加しても、最初は既存権限を正本として読み、新権限との比較ログだけを残す。
3. 既存値から新権限への割当を、利用者ごとに業務担当者が確認する。
4. APIを「新権限優先、未移行者は既存値へ安全側フォールバック」にする。
5. フロントを新API応答へ切り替える。
6. 管理者、編集者、閲覧者、金額非表示、本人で直接APIを含むテストを行う。
7. 全員移行後も既存列は直ちに削除せず、少なくとも一運用期間はロールバック用に保持する。

未知値・空欄を強い権限へ変換しない。ShiftBuilder空欄6人は自動で `view` や `edit` にせず、必要業務を確認して割り当てる。

## 9. 変更予定と影響範囲

業務判断承認後に変更候補となる範囲。

- Account API: 共通権限コンテキスト取得、権限割当管理、監査ログ
- Account Console: 権限編集UI、自己昇格・最後の管理者保護
- Dashboard: 共通権限応答による入口表示
- OrderCase GAS: 操作別権限、金額、店舗、アーカイブの分離
- OrderCase画面: 操作別ボタン表示・理由表示
- ShiftBuilder GAS: `self` のレスポンス絞り込み、確定・公開API、状態遷移保護
- ShiftBuilder画面: `manager`／`edit` の操作差、確定・公開UI
- 勤怠GAS: 独自role一覧から正式権限への移行
- 勤怠管理画面: 管理・位置情報権限の分離
- 新規シート候補: `permission_assignments`
- API契約: `capabilities`、`scopes`、共通の権限不足コード

## 10. 安全な実装順

1. 業務判断と既存利用者の移行表を確定
2. 権限割当表と共通権限コンテキストを読み取り専用で追加
3. 旧判定との比較テストを行い、不一致を可視化

## 13. えいちが承認した基本方針

2026-08-07、えいちは次の6点を基本方針として承認した。

1. `role` は所属・契約区分として残し、操作権限に使わない。
2. Account Console管理はroleではなく、明示的なアカウント管理権限で決める。
3. OrderCaseは金額編集、案件アーカイブ、店舗アーカイブを通常編集から分ける。
4. 旧ShiftBuilder値は移行候補として `edit`＝下書き編集、`manager`＝確定・公開候補、`all`＝例外解除候補と比較する。ただし、新体系では組織階層とShift編集権限を別々に判定する。
5. `self` は本人の公開済み予定だけを返す。
