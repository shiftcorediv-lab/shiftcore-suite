# 03 権限設計ロードマップ

- 更新日: 2026-08-10
- 対象: ShiftCore Suite 全体
- 状態: Shadow基盤、組織階層、developer全権・業務名簿非表示を本番反映済み。実効権限は旧体系のまま。独立監査の是正をローカル実施中
- 正本候補: Account Console の `users_master`

## 1. 目的

ShiftCore Suite 全体で、誰がどの画面・データを閲覧、作成、編集、確定、公開、アーカイブできるかを正式に決める。

対象は次を含む。

- 共通ログインとDashboard
- Account Console
- OrderCase
- ShiftBuilder
- 出発・入店・終了報告
- 実績報告
- 労務管理
- 月間Dashboard

## 2. 作業原則

- 既存の `role` や権限値を、根拠なく追加・改名しない。
- 01のAccount Console棚卸しを重複して作り直さない。
- 02の案件、時刻、配置、金額、店舗マスター実装を権限設計の都合で作り直さない。
- 画面上の非表示だけを防御にせず、API／GAS側で最終判定する。
- 「何を操作できるか」と「誰のデータまで見られるか」を分けて設計する。
- 空欄や旧値を、強い権限へ自動補完しない。
- 認証、権限、DB・シート列、API契約、本番設定は、設計と影響範囲の承認前に変更しない。
- commit、push、PR、GAS反映、デプロイ、公開は、えいちの明示承認なしに行わない。

## 4. 推奨する基本設計

当面は既存の `users_master` を権限の正本とする。

参照経路は次へ統一する。

```text
Firebaseログイン
  → Account APIで本人確認
  → users_masterから状態・利用機能・詳細権限を取得
  → 各アプリAPI／GASが操作ごとに再判定
  → 許可された範囲のデータだけを返す／変更する
```

フロント画面は、APIが返した権限に合わせてボタンを隠す、無効にする、説明を表示する。フロントの判定だけで操作を許可しない。

操作権限は `permission_assignments`、組織階層と直属関係は別の正式な組織情報として扱う。既存の自由入力 `position` を権限判定へ直接使わない。

組織階層は次の4段階とする。

```text
役員 > マネージャー > リーダー > メンバー
```

- `role` の `admin`／`developer` 等はシステム上の利用者区分であり、この組織階層とは別軸。
- `developer` は全アプリのシステム特権を持つ。個別モジュール・詳細権限列には依存しないが、停止中アカウント、自己変更禁止、整合性検証、監査ログの統制は免除しない。
- `developer` はShiftBuilderの配置候補・人員軸・配置済み表示およびPMOの新規月次人員名簿から除外する。ログイン・管理操作・配置履歴・監査履歴からは除外しない。作成済みPMO月次シートはrole列を持たないため、自動改変せず移行前に実データを読み取り確認する。
- 既存の `shiftbuilder_permission=manager` はShiftBuilder専用の旧権限値であり、組織上のマネージャーとは別物。
- リーダー以上は全社の案件・シフト・配置・非推奨理由を閲覧できる。
- リーダー未満は本人の公開済み予定だけを閲覧できる。
- 申請承認は全社閲覧と分離し、申請者の直属管理者本人だけに許可する。

## 5. 決裁済みの組織階層と操作権限

次の名称は組織上の階層であり、既存 `role` へ同名値を追加する決定ではない。正式な保存形式と既存利用者への割当は移行設計で確定する。

| 操作 | メンバー | リーダー | マネージャー | 役員 |
|---|---:|---:|---:|---:|
| 本人の公開済み予定を見る | 可 | 可 | 可 | 可 |
| 全社の案件・シフト・配置を見る | 不可 | 可 | 可 | 可 |
| 金額・単価を見る | 不可 | 可 | 可 | 可 |
| 非推奨理由を見る | 不可 | 可 | 可 | 可 |
| 案件を登録する | 不可 | 可 | 可 | 可 |
| 案件を編集する | 不可 | 不可 | 可 | 可 |
| 金額・単価を編集する | 不可 | 不可 | 可 | 可 |
| 指名・NGを登録・解除する | 不可 | 不可 | 可 | 可 |
| 案件・店舗をアーカイブ・復元する | 不可 | 不可 | 可 | 可 |
| Shiftを確定・公開する | 不可 | 不可 | 可 | 可 |
| 案件ランクを変更する | 不可 | 不可 | 不可 | 可 |
| マネージャーを任命・解除する | 不可 | 不可 | 不可 | 可 |

Shiftの配置・入替・解除は組織階層ではなく、Shift編集権限を明示的に持つ利用者だけに許可する。

申請承認は直属限定とする。リーダーは直属メンバー、マネージャーは直属リーダー、役員は直属マネージャーの申請だけを承認対象とする。上位者であっても直属管理者でなければ承認できず、全社閲覧権限だけでも承認できない。

役員本人の申請は自己承認を禁止し、指定された別の役員が承認する。役員の申請・承認は監査ログへ残して、申請者・承認者以外のactiveな役員と独立した監査担当へ通知する。activeな役員が1人だけなら役員本人の申請を拒否し、2人だけなら独立監査担当への通知を必須とする。ログは談合の発見と抑止に使うが、ログだけに依存せず、申請者と承認者の分離、定期レビュー、ログ改ざん検知を組み合わせる。

## 6. フェーズ別ロードマップ

### Phase 0: 基線と実データの確定

目的: 誤ったブランチや古い引き継ぎを基準にしない。

- 01の正式な引き継ぎ・現状資料の所在を特定する。
- 02の監査結果、公開コミット、OrderCase GAS版、ShiftBuilder GAS版を特定する。
- 本番の `users_master` から、個人情報を残さない形で既存 `role`、モジュール、詳細権限の使用値と件数を確認する。
- ShiftBuilder GASを読み取り可能な正規の保管先へ揃え、全アクションの認証・権限判定を監査する。
- OrderCaseの「1案件＝1人分」と複数名配置のデータ契約を整理する。

完了条件:

- ローカル、Git、GAS、本番公開版の対応表がある。
- 既存ユーザーの権限値を推測せず把握できている。
- 未確認のGAS権限判定が残っていない。

### Phase 1: 業務判断の確定

目的: 誰に何を許可するかを、利用者に分かる言葉で確定する。

決める項目:

1. Account Consoleでユーザーと権限を変更できる人
2. OrderCaseで金額を閲覧・編集できる人
3. 案件をキャンセル・アーカイブできる人
4. 店舗マスターを編集・アーカイブ・復元できる人
5. ShiftBuilderで配置・入替・解除できる人
6. ShiftBuilderで確定できる人
7. ShiftBuilderで公開・配布できる人
8. `self` に表示する予定の状態と範囲
9. 全社、所属組織、担当エリア、本人のデータ範囲
10. 勤怠承認と正確な位置情報閲覧を許可する人

2026-08-10決裁:

- 組織階層は役員、マネージャー、リーダー、メンバーの4段階。
- リーダー以上は全社閲覧、リーダー未満は本人の公開済み予定だけ。
- 案件登録はリーダー以上、案件編集はマネージャー以上。
- 金額閲覧はリーダー以上、金額編集はマネージャー以上。
- Account Consoleの利用者・権限変更、指名・NG編集、アーカイブ・復元、Shift確定・公開は基本マネージャー以上。
- 案件ランク変更とマネージャーの任命・解除は役員。
- Shiftの配置・入替・解除は階層ではなくShift編集権限で決める。
- 申請承認は申請者の直属管理者本人に限定し、全社閲覧と分離する。
- `self` は本人の公開済み予定だけを返す。
- 勤怠承認と正確な位置情報閲覧は別権限とする。

完了条件:

- 利用者向け権限表をえいちが承認している。
- 既存の権限値へ割り当てる部分と、新しい権限が必要な部分が分かれている。

### Phase 2: 権限契約と移行設計

目的: 実装者ごとの解釈差をなくす。

- 操作ごとに必要権限とデータ範囲を定義する。
- Account APIの共通ユーザー応答を定義する。
- 各APIの成功、認証切れ、権限不足、対象外データの応答を統一する。
- 既存値、空欄、未知値の扱いを決める。
- 旧画面と新API、新画面と旧APIが一時的に混在する段階移行を設計する。
- Shadow判定は旧権限から例外隔離し、capabilityとscopeの両方を比較する。勤怠は独自権限の棚卸し完了まで比較対象外とする。
- JSTの専用日付列、排他制御、緊急停止フラグ、ログ欠落の健全性表示をShadow契約に含める。
- 既存ユーザーごとの移行表とロールバック方法を作る。

完了条件:

- 画面とAPIの権限マトリクスが一致している。
- シート列・API変更の要否と影響範囲が確定している。
- 自動的な権限昇格が発生しない移行手順がある。

### Phase 3: サーバー側の防御

目的: URL直打ちやAPI直接呼び出しでも権限を越えられないようにする。

推奨順:

1. Account APIが `shiftbuilder_permission` を含む必要な詳細権限を返す。
2. Account Console APIの管理条件を正式な管理権限へ合わせる。
3. OrderCaseの閲覧、金額、編集、店舗管理、アーカイブを操作単位で守る。
4. ShiftBuilderの閲覧、配置、解除、入替、確定、公開、配布を操作単位で守る。
5. `self` と組織・エリア範囲をAPIレスポンス段階で絞る。
6. 勤怠の独自role判定を正式な権限参照へ置き換える。
7. 権限変更と重要操作の監査ログを残す。

完了条件:

- 権限不足のAPI直接呼び出しがすべて拒否される。
- 他人・他組織・他エリアのIDを指定しても取得・変更できない。
- 画面を経由しなくても同じ制御が効く。

### Phase 4: フロント画面の統一

目的: 利用者が自分の権限と操作不可理由を理解できるようにする。

- Dashboardのモジュール入口を最新権限で表示する。
- 各画面で権限名を利用者向けの言葉に統一する。
- 操作不可のボタンを非表示または無効化し、理由を表示する。
- 権限変更後の再読込・再ログイン案内を統一する。
- 読込中、空データ、権限不足、通信失敗を区別する。
- 狭い画面でも権限表示と重要操作が判別できるようにする。

完了条件:

- 画面の表示とAPIの許可が一致する。
- 利用者が「なぜ操作できないか」を理解できる。

### Phase 5: 移行・検証・段階反映

目的: 既存利用者を締め出したり、意図せず権限を広げたりせず反映する。

- 既存ユーザーを移行表に沿って更新する。
- 管理者、編集者、閲覧者、金額非表示、本人のテストアカウントで確認する。
- 旧キャッシュ、停止ユーザー、権限変更直後、再ログインを確認する。
- OrderCaseの案件保存、金額、店舗、アーカイブ連動を回帰確認する。
- ShiftBuilderの配置、解除、入替、確定後保護、公開を確認する。
- GAS、静的画面、必要なデータ移行を安全側の順序で段階反映する。
- 反映後に直接API呼び出しを再確認する。

完了条件:

- 既存利用者の必要業務が維持されている。
- 権限を持たない人の画面操作とAPI操作が拒否される。
- ローカル、テスト、commit、push、GAS、公開、本番データの状態が区別して記録されている。

### Phase 6: 04以降の権限拡張

04以降の仕様確定後に扱う。

- 出発・入店・終了報告の本人操作と代理操作
- 実績報告の閲覧、修正、差戻し、確定
- 労務情報と正確な位置情報の閲覧
- 月間Dashboardの全社・組織・本人集計
- 外部人員と所属法人管理者の閲覧範囲

これらは仕様確定前に権限値やシート列を追加しない。
