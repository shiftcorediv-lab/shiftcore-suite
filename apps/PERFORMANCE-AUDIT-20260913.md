# Another Portal 全体速度調査・対策案

調査日: 2026-09-13 / 対象: 現行ポータル全体 / 依頼: 原因調査と対策考案。

## 結論

単にキャッシュの有効期間が短いことだけでは説明できない。優先対象は、勤怠のシフト全体同期、通知を含む長い排他区間、実績管理の繰り返し読み取り、オフの参照処理まで含む全体ロック。

遅延自体は本番実行履歴で確認済み。ただし、各処理の所要時間を同じ要求IDで結び付ける記録が不足しており、101秒の何秒が認証・外部通信・シート処理・ロック待ちだったかは未確定。コード上の改善余地を、そのまま本番の遅延寄与率や改善秒数に読み替えない。

製品コード・公開設定・業務データの変更、打刻、保存、メール送信は今回実施していない。報告書のみ追加。前回の未公開4ファイルは保持。

## 2. コードで確認した負荷の構造

以下のパスは本報告書のある apps ディレクトリ基準。ローカルHEADは73a3874。全GASの公開ソースを今回再取得して完全一致比較したわけではないため、コード上の分析と本番実測を分ける。

### A. 勤怠管理が一覧更新のたびに当月シフト全体を同期する【優先度1】

- `account-console/backend/attendance-apps-script/Code.gs:1666` の `getAdminDashboard_` → `getSchedules_`（1997）→ `syncSchedules_`（2042）。
- シフトAPIの `shiftBuilderGetMonthData` を area=all で呼び、全案件の配置から予定を再構築・差分保存。その後、表示日付で絞る。
- 過去日・月の一覧を見る場合も同期対象は現在月。過去日の表示更新に現在月全体取得の待ちが入り得る。
- ダッシュボード向けには同期済み判定・同時同期抑止の `getDashboardSchedules_` があるが、管理一覧はこの経路を利用しない。
- 対策: 「予定同期」と「勤怠一覧取得」を分離。既存予定＋最新打刻で一覧を返し、予定の変更確認を別に扱う。シフト変更の反映保証を定義してからキャッシュを使う。
- 期待効果: 通常の一覧更新からシフト全体取得1回を外せる。削減秒数は未測定。

### B. 出発・最寄り到着の保存ロック内に外部同期と通知がある【優先度1】

- 同ファイル550の `submitFieldReport_` は20秒上限のロック取得後に予定を照合。`findSchedule_` / `findScheduleById_`（2343付近）は、既存行が引数で渡されない場合 `getSchedules_` を呼ぶ。
- 保存・再読込の後も `notifyManagers_`（1957）を同期実行。メール処理が終わるまで応答もロック解放も行われない。
- 「通知失敗でも保存成功を返す」は実装済みだが、「通知を待たずに返す」にはなっていない。
- 対策: 外部参照を排他区間の前に移し、区間内では予定・重複・順序の必要な再確認と保存だけ行う。通知は配送待ち記録を確実に保存してから既存の定期処理等で送る設計を検討。
- 単にメール処理を呼ばなくする・非同期呼出しを放置する案は不可。通知漏れ、重複、再送、送信までの遅れを定義する。
- ロックの削除ではなく短縮。二重打刻・入店後の到着追加防止を維持する。

### C. 実績管理に件数比例の同一シート再読込【優先度1】

- 同ファイル1150付近 `buildWorkReportAdminData_` は予定、報告、回答、改訂、通知、勤怠を全件読み、後から期間を絞る。
- 未報告の終了済み勤務ごとに `workReportTemplateForContext_`（1536）を呼び、共通のマッピング表・テンプレート表を再読込する。
- 実関数を隔離し、架空の未報告100件・有効な対応設定で検査。現行引数では `rows_` 呼出し200回。同じ関数の既存引数へ先読みした配列を渡す場合は2回。これは論理的な関数呼出し数であり、実ネットワーク往復数や速度100倍の証明ではない。
- 対策: 1要求内で設定表を一度だけ取得して使い回す。その後、一覧に不要な改訂詳細を詳細表示時へ分ける。キャッシュ期間を延ばさなくても改善できる。
- シート列構造検査も6シートで毎回実施（2401）。まず時間を測り、検査自体の撤去はしない。

### D. オフの参照まで全体ロックに入る【優先度1】

- `pmo/backend/pmo-apps-script/api.js:43`。締切GET相当のみロック外。他の本人確認、一覧、メタ、Excel、提出が同じScriptLockで10秒待つ。
- 認証の外部通信もロック内。Excel生成が一覧や提出を待たせる構造。
- `monthly_sheet.js:658` の一覧は認証後、現行名簿を別のAccount APIから取得して一覧を再構築（224）。
- 対策: 純粋な参照をロックから外す。ただし `getOrCreateRequestSheet` 等の作成を伴う初期化は分離し、無条件に全読取を非排他にしない。Excelの一時ファイルは個別管理し、提出の原本整合性を守る。
- 締切については既に分離済み。再実装不要。

### E. シフトが当月・前月・候補者を揃えてから表示完了とする【優先度2】

- `shiftbuilder/js/shiftbuilder/main.js:2245` 以降で3取得を開始。既に並列なので「並列化する」だけの提案は無効。
- 当月取得後も前月を待ち、候補者取得まで月の読込表示を維持（2207付近）。
- `backend/shiftbuilder-apps-script/repositore.js:534` は案件・日付・代理店・店舗・配置・メンバーを読み込んで月データを作る。本人照合と表示用メンバーの取得も重複し得る。
- クライアントの60秒キャッシュは既にある（`js/shiftbuilder/api.js:12`）。
- 対策: 当月を先に描画し、前月比較や候補者が必要な機能のみ待機。未取得を「不足なし」「配置可能」に読み替えない。要求内の共通シート読込を共有する。
- PCの月間一望性を損なうページ分割や横スクロール化はしない。

### F. メンバー初期表示に全体履歴が含まれる【優先度2】

- `account-console/backend/account-apps-script/account_console_users.js:22` は、本人確認・一覧・権限があれば変更履歴もまとめて返す。
- 統合取得は既に実装済み。さらに本人検索は名簿全体を読む（`users.js:49`）、一覧でも再取得する。
- 対策: 同一要求内の名簿読込を共有し、初期一覧に不要な履歴は選択時へ移す。権限に応じた絞り込みは維持。
- 今回のAccount実行時間は他と比べ短い。全体の最優先とはしない。

### G. オーダー・店舗・代理店の共通データ取得【優先度2】

- `ordercase/backend/ordercase-apps-script/Service_Bootstrap.js:11` は案件種別・代理店・店舗・設定を読む。初期表示統合は既に存在。
- 案件一覧は60秒キャッシュが存在（`Service_ListPage.js:6`）。一方、登録用共通データは当該関数でキャッシュしていない。

- 対策: マスター共通結果を適切な範囲で共有し、変更時に版を更新。停止・アーカイブ・代理店の店舗関係も更新対象。

### H. 新規タブのヘッダーが別途本人情報を取得【優先度2】

- `theme/shiftcore-theme.js:207`。sessionStorageに本人情報がなければ共通ヘッダー独自にAccount APIを呼ぶ。本文側も認証済み取得を行う。
- 同ヘッダー内の重複抑止はあるが、本文の要求と共有しているわけではない。
- 対策: 同じ画面の初期API結果からヘッダーへ本人情報を供給するか、同時進行の本人確認を共有する。入口だけの認証に変更しない。

### I. 待ち時間上限・エラー応答の扱いが統一されていない【優先度2】

- メンバー初期取得は20秒＋最大1回再試行、オフ管理は60秒。オーダー共通fetchには当該関数内で上限なし。
- 勤怠管理の60秒上限と不正応答から前回表示を守る対策は前回ローカル修正のまま未公開。
- 対策: 読取・更新を区別。更新の結果不明は再送ではなく結果照合。期限を延ばすだけでは高速化にならない。ブラウザが中断してもGAS処理が停止する保証はない。

## 3. 既にある対策／過剰に変えない部分

- 勤怠管理は非表示時の自動更新停止、操作中の更新抑止、同じタブのinFlight共有を実装済み。30秒は取得終了後の次回待ちであり、常に30秒ごとに要求が積まれるわけではない。
- ダッシュボードは保存済み表示、成績・通知の後段取得、予定同期の重複抑止を実装済み。新規に同じ仕組みを重ねない。
- シフトの並列取得・保存キュー・読取キャッシュ、オフとメンバーの初期統合取得も存在する。
- 認証キャッシュは現行コードに既に存在する。オーダー読取900秒、勤怠の一部読取900秒、シフトのメール解決300秒。以前の「本人情報は毎回確認」は提案方針であり、現行実装が全てそうであるという意味ではない。今回の調査で勝手に削除・延長しない。
- ログイン画面のCSS圧縮・ロゴ最適化を最優先にしない。ルーター廃止、Blue/Red廃止、ドメイン変更の根拠は得られていない。

## 4. 推奨する実装順と合格条件

1. **短い計測を追加**: アクション名、相関ID、総時間、認証・外部取得・ロック待ち・シート読取/書込・通知・描画までの時間、キャッシュ命中、件数のみ。個人名・本文・トークン・位置情報は記録しない。勤怠管理は既存の段階計測対象から漏れているため最優先。
2. **要求内の再読込削減**: 実績の設定表と名簿を一度読みへ。期間を越える長期キャッシュや権限変更が不要で、副作用が比較的小さい。
3. **勤怠一覧から予定全体同期を分離**: 一覧の最新打刻表示を予定同期から独立。配置変更時・他端末・同期失敗時の挙動を検証。
4. **保存の排他区間と通知の分離**: 二重保存防止、結果照合、通知配送待ちの確実な記録を維持。通知に許容する遅延は事前確認。
5. **オフの読取ロック分離**: 初期化と純粋読取を分ける。締切前の回収を壊さないよう段階公開。
6. **シフト当月先行表示・履歴の後読み・初期取得共有**。
7. **変更検知と組み合わせた長めのキャッシュ**。それでも目標未達の処理だけ保存基盤の変更を検討。

各段階で同じアカウント区分・同じ月・同じデータ件数・同じ端末条件を揃える。読み取りは制御された逐次サンプルで中央値・95パーセンタイル・失敗率を比較し、初回/再訪、キャッシュ命中/不命中を分ける。GAS実行時間だけでなく、押下→保存確定→操作可能まで測る。

提案する目標（達成保証ではない）: 通常の勤怠保存は中央値3秒以内・95%が5秒以内、保存済み画面の先行表示は1秒以内。全体一覧の目標は件数別の基準測定後に固定。未達なら待機表示でごまかさず追加原因を記録する。

分離テスト環境で同時2〜5操作、同一人の連打、応答喪失、別端末更新、権限変更、締切前後を検査。本番で大量要求や架空の打刻を発生させる負荷試験は今回行っていない。

## 5. キャッシュ案の条件

- 最初に1要求内の再利用を行う。これだけなら次の要求には最新確認が入る。
- 店舗・代理店等は30〜60分を初期候補とし、更新版の変更で破棄。実測で必要なら延長する。
- シフトは予定の最新版と取得時刻を分け、変更検知が失敗しても古い予定を無期限に確定情報として使わない。現行のlocalStorage通知は同じブラウザ・origin内であり、別端末まで届かない。
- 勤怠・申請は保存結果を即反映。承認と保存はサーバーで必要な本人・権限・状態確認を維持。
- 権限別・本人別・環境別の結果を混ぜない。ログアウト/別アカウント時は個人用キャッシュを破棄。
- Apps Script CacheServiceは最大6時間・1キー100KB、期限前に消える場合もある。「1日保持」をこの仕組みだけで保証できない。キャッシュが消えても原本から復旧する設計が必要。[Google公式仕様](https://developers.google.com/apps-script/reference/cache/cache?hl=ja)

## 6. 未確定事項と調査の限界

- 101秒の内訳、GAS呼出し前後のGoogle側待ち、認証中継経路ごとの実時間は未確定。実行履歴の長さだけでGoogle障害・認証過剰・ネットワーク不良と断定しない。
- 認証後各画面の冷起動ネットワークトレース、スマホ実機、一般スタッフの本番保存の性能測定は未実施。プロファイル移植や認証情報取り出しは行っていない。
- ローカル解析したGAS全ソースと現行公開版の完全な再照合、キャッシュの実命中率、スプレッドシート数式の再計算負荷は未測定。
- 読取の全体調査で保存処理のコードは確認したが、実書込は実行していない。配置・勤怠・実績の保存速度を検証済みとはしない。
- 追加有料サービスや基盤移行はまだ必要と判断していない。まず現行構成の重複取得・長い排他・読込順を直して評価する。

## 7. 公式資料との照合

Googleの公式指針も、外部サービスへの呼出し削減、一括読取とメモリ内処理、キャッシュ再利用を推奨している。この一般指針は今回のコード所見を補助するもので、個々の遅延原因の証明ではない。[Apps Script ベストプラクティス](https://developers.google.com/apps-script/guides/support/best-practices?hl=ja)

速度診断スキルの手順に沿ってフロント計測とサーバー実行履歴を区別した。LCPの良さを業務操作の軽さと混同せず、既存の改善を重複提案から除外した。
